# 银行家算法 (Banker's Algorithm)

## 概述

**银行家算法**是由 Edsger Dijkstra 于 1965 年提出的[[死锁]]避免算法。其名称来源于银行家发放贷款的策略：银行家不会将全部资金贷出，而是保留一部分储备金，确保能够满足所有客户的取款需求。

> **核心思想**：每次资源分配前，系统模拟分配并检查是否处于**安全状态**（即存在一个安全序列）。只有不会导致死锁的请求才被批准。

---

## 核心数据结构

假设系统有 $n$ 个进程和 $m$ 种资源类型：

| 数据结构 | 符号 | 维度 | 说明 |
|---------|------|------|------|
| **Available** | `Available[m]` | 一维数组 | 每种资源的可用实例数量 |
| **Max** | `Max[n][m]` | 二维矩阵 | 每个进程对每种资源的最大需求 |
| **Allocation** | `Allocation[n][m]` | 二维矩阵 | 当前已分配给每个进程的资源数 |
| **Need** | `Need[n][m]` | 二维矩阵 | 每个进程还需要的资源数 |

**关系**：
$$
\text{Need}[i][j] = \text{Max}[i][j] - \text{Allocation}[i][j]
$$

---

## 算法组成

银行家算法由两部分组成：

### 1. 安全性算法 (Safety Algorithm)

> 判断系统当前是否处于安全状态。

**步骤**：

1. 初始化 `Work[m] = Available[m]`，`Finish[n] = {false}`
2. 找到一个 $i$ 使得：
   - `Finish[i] == false`
   - `Need[i] <= Work`（Need[i] 的每个分量 ≤ Work 的对应分量）
3. 若找到，则：`Work = Work + Allocation[i]`，`Finish[i] = true`，回到步骤 2
4. 若所有 `Finish[i] == true`，则系统处于**安全状态**；否则处于不安全状态

> 找到的进程顺序即为一个**安全序列**。

### 2. 资源请求算法 (Resource-Request Algorithm)

> 处理进程 $P_i$ 的显式请求 `Request[i]`。

**步骤**：

1. 若 `Request[i] <= Need[i]`，转步骤 2；否则报错（进程超过最大需求）
2. 若 `Request[i] <= Available`，转步骤 3；否则进程必须等待
3. **假装分配**（试分配）：
   - `Available = Available - Request[i]`
   - `Allocation[i] = Allocation[i] + Request[i]`
   - `Need[i] = Need[i] - Request[i]`
4. 调用**安全性算法**检查是否安全
   - 若安全 → 批准分配
   - 若不安全 → 回滚分配，进程等待

## 完整示例

### 初始状态

| 进程 | Allocation（已分配） | Max（最大需求） | Need（还需） |
|:----:|:---:|:---:|:---:|
| | A B C | A B C | A B C |
| P₀ | 0 1 0 | 7 5 3 | 7 4 3 |
| P₁ | 2 0 0 | 3 2 2 | 1 2 2 |
| P₂ | 3 0 2 | 9 0 2 | 6 0 0 |
| P₃ | 2 1 1 | 2 2 2 | 0 1 1 |
| P₄ | 0 0 2 | 4 3 3 | 4 3 1 |

**Available** = (3, 3, 2)

### 判断安全状态

1. Need[P₁] = (1, 2, 2) ≤ Available = (3, 3, 2) → P₁ 可满足
   - 假设 P₁ 完成，回收：Work = (3,3,2) + (2,0,0) = (5,3,2)
   - Finish[P₁] = true

2. Need[P₃] = (0,1,1) ≤ Work = (5,3,2) → P₃ 可满足
   - 回收后：Work = (5,3,2) + (2,1,1) = (7,4,3)
   - Finish[P₃] = true

3. Need[P₄] = (4,3,1) ≤ Work = (7,4,3) → P₄ 可满足
   - 回收后：Work = (7,4,3) + (0,0,2) = (7,4,5)
   - Finish[P₄] = true

4. Need[P₀] = (7,4,3) ≤ Work = (7,4,5) → P₀ 可满足
   - 回收后：Work = (7,4,5) + (0,1,0) = (7,5,5)
   - Finish[P₀] = true

5. Need[P₂] = (6,0,0) ≤ Work = (7,5,5) → P₂ 可满足
   - 回收后：Work = (7,5,5) + (3,0,2) = (10,5,7)
   - Finish[P₂] = true

✅ **安全序列**：\<P₁, P₃, P₄, P₀, P₂\>，系统处于安全状态。

## 算法特点

### 优点
- 在运行时动态判断安全性，比死锁预防更高效
- 允许更高的资源利用率

### 缺点
- 进程必须**预先声明**最大资源需求（现实中难以做到）
- 进程数量必须**固定**（无法处理动态创建进程）
- 资源数量必须**固定**（无法处理热插拔资源）
- 所有进程必须是**无关的**（不存在同步约束）
- 算法复杂度为 $O(m \times n^2)$，大系统中开销高

## 与其他死锁处理策略对比

| 策略 | 资源利用率 | 实现难度 | 适用场景 |
|------|:---------:|:--------:|---------|
| **死锁预防** | 低 | 低 | 嵌入式、实时系统 |
| **银行家算法** | 中 | 高 | 资源需求可预知的系统 |
| **死锁检测+恢复** | 高 | 中 | 通用操作系统（如数据库） |
| **鸵鸟策略** | 最高 | 最低 | 桌面系统（死锁极为罕见时） |

## 常见问题

### Q1：安全状态一定不会发生死锁吗？
> **是的**。安全状态意味着至少存在一个安全序列，系统可以按该序列分配资源，保证所有进程都能完成。

### Q2：不安全状态一定会发生死锁吗？
> **不一定**。不安全状态意味着**可能**发生死锁，但死锁不一定发生。银行家算法保守地拒绝所有可能导致不安全状态的请求，因此可能拒绝实际安全的请求。

### Q3：银行家算法有什么实际应用？
> 银行家算法本身在实际操作系统中很少直接使用（因为需要预知最大需求），但其思想被用于：
> - 数据库系统的事务并发控制
> - 网络流量工程
> - 嵌入式系统资源管理
